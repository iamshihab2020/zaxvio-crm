## Invoices

Invoice management with payment tracking. **22 endpoints.**

> **Status is derived, not chosen.** `draft`, `sent`, `partially_paid`, `paid` and
> `void` are stored, but the money statuses are computed from the payment rows by
> `services/invoices/status.service.ts` — recording or deleting a payment is the
> only way an invoice becomes `partially_paid` or `paid`. `overdue` is never
> trusted from the column: every reader derives it from `due_date` against the
> tenant's today. See the transition table under `PATCH /invoices/:id/status`.

### `GET /invoices`

**Auth:** `requireTenant`

List invoices with filtering and pagination.

**Query Parameters:**

| Parameter | Type | Default | Options |
|-----------|------|---------|---------|
| `search` | string | - | Searches invoiceNumber, notes, customer name. LIKE wildcards are escaped. |
| `status` | string | - | `draft`, `sent`, `paid`, `partially_paid`, `overdue`, `void`, `unpaid` |
| `customerId` | uuid | - | Filter by customer |
| `jobId` | uuid | - | Filter by linked job |
| `dateFrom` | string | - | `YYYY-MM-DD` — inclusive lower bound on `issuedDate` |
| `dateTo` | string | - | `YYYY-MM-DD` — inclusive upper bound on `issuedDate` |
| `showArchived` | boolean | `false` | Return archived invoices instead of active ones |
| `page` | integer | `1` | - |
| `limit` | integer | `20` | Max: 100 |
| `sortBy` | string | `"createdAt"` | `createdAt`, `issuedDate`, `dueDate`, `invoiceNumber`, `status`, `totalAmount`, `balanceDue` |
| `sortOrder` | string | `"desc"` | `asc`, `desc` |

> `overdue` and `unpaid` are **derived** filters, not stored statuses. `overdue`
> compares `due_date` against the tenant's today (the status column lags until the
> cron runs). `unpaid` means "money is still owed" — `sent`, `overdue` or
> `partially_paid` — and exists so the customer overview can ask the database for
> outstanding invoices rather than filtering one page of results in the browser.

**Response** `200 OK`

      "status": "sent",
      "issuedDate": "2026-03-29",
      "dueDate": "2026-04-28",
      "subtotal": "450.00",
      "taxRate": "0.0825",
      "taxAmount": "37.13",
      "discountAmount": "0.00",

      "creditAmount": "0.00",
      "notes": "Thank you for choosing Smith HVAC!",

### `GET /invoices/stats`

**Auth:** `requireTenant`

Status counts and outstanding money in one query. Honours the same filters as the
list, so a customer-scoped page gets customer-scoped KPI cards.

**Query Parameters:** `customerId`, `jobId`, `dateFrom`, `dateTo`, `showArchived`
— all optional, same semantics as `GET /invoices`.

**Response** `200 OK`

```json
{
  "data": {
    "draft": 3,
    "sent": 11,
    "paid": 47,
    "overdue": 4,
    "partially_paid": 2,
    "void": 1,
    "outstanding": "6210.45",
    "overdueAmount": "1830.00"
  }
}
```

`overdue` and `overdueAmount` are derived from `due_date` in the tenant's
timezone — the same predicate the list filter and the dashboard banner use.

### `POST /invoices`

**Auth:** `requireTenant`

Create a new invoice. `invoiceNumber` is generated by a database trigger
(`INV-YYYY-NNNN`, per tenant per year, under a per-tenant advisory lock). If
`jobId` is provided, line items are copied from the job — and the job must belong
to `customerId`, or the request is refused.

The whole creation is one transaction: insert, copy line items, recalculate. A
failure part-way leaves nothing behind.

**Request Body:**

```json
{
  "customerId": "cust_001",
  "jobId": "job_001",
  "issuedDate": "2026-03-29",
  "dueDate": "2026-04-28",
  "taxRate": "0.0825",
  "discountAmount": "0",
  "notes": "Thank you for choosing Smith HVAC!"
}
```

| Field | Type | Required | Description |
|-------|------|----------|-------------|
| `customerId` | uuid | Yes | Must belong to the tenant |
| `jobId` | uuid | No | Copies the job's line items and tax rate. Must belong to `customerId`. |
| `issuedDate` | string | No | `YYYY-MM-DD`. Defaults to today **in the tenant's timezone**. |
| `dueDate` | string | No | `YYYY-MM-DD`. Derived from the tenant's `invoicePaymentTerms` when omitted — "Net 30" → issued + 30 days, "Due on receipt" → the issue date. Terms with no computable date (e.g. "50% up front") leave it null. |
| `taxRate` | string | No | A **fraction**, 0–1. `"0.0825"` is 8.25%. Ignored when `jobId` is set (the job's rate wins). |
| `discountAmount` | string | No | Flat discount, e.g. `"25.00"` |
| `notes` | string | No | Max 5000 characters |

> There is no `lineItems` field. Line items are added through
> `POST /invoices/:id/line-items`, or copied from a job via `jobId`.

**Response** `201 Created` — the full invoice row, with the generated
`invoiceNumber` and recalculated totals.

**Errors:** `400` — customer not found · job not found · *"That job belongs to a
different customer"* · *"An active invoice already exists for this job (INV-…)"*
(with `existingInvoiceId`).

### `PATCH /invoices/:id`

**Auth:** `requireTenant`

Update invoice fields. **Draft only**, and never on an archived invoice.
Recalculates totals inside the same transaction when `taxRate` or
`discountAmount` changes.

**Request Body** (all optional): `notes`, `dueDate` (nullable), `taxRate`,
`discountAmount`, `customerId`, `issuedDate`.

**Response** `200 OK` — the updated invoice.

**Errors:** `404` — not found · `400` — *"Only draft invoices can be edited"* ·
*"Cannot modify an archived invoice. Restore it first."* · customer not found.

### `DELETE /invoices/:id`

**Auth:** `requireTenant`

Hard delete. **Draft only.** Removes line items and payments by cascade, and
deletes the stored PDF from R2.

**Response** `200 OK`

```json
{ "message": "Invoice deleted" }
```

**Errors:** `400` — *"Only draft invoices can be deleted"* · archived.

## Invoice Line Items

Sub-resource under `/invoices/:id/line-items`. Every operation recalculates the
invoice's totals **and its status** in the same transaction, and every one is
refused on a non-draft or archived invoice.

### `POST /invoices/:id/line-items`

**Auth:** `requireTenant`

Supply the fields directly, or a `catalogItemId` to fill `description`,
`unitPrice` and `itemType` from the catalog. A catalog item belonging to another
tenant is rejected rather than silently stored.

**Request Body:**

```json
{
  "itemType": "part",
  "description": "Air Filter - 20x25x1 MERV 13",
  "quantity": "4",
  "unitPrice": "18.50",
  "catalogItemId": "cat_007"
}
```

| Field | Type | Required | Description |
|-------|------|----------|-------------|
| `description` | string | Yes* | Max 500 chars. *Optional when `catalogItemId` supplies it. |
| `unitPrice` | string | Yes* | e.g. `"18.50"`. *Optional when `catalogItemId` supplies it. |
| `itemType` | string | Yes* | `labor`, `part`, `material`, `service_call`, `other` |
| `quantity` | string | No | Positive number, default `"1"` |
| `catalogItemId` | uuid | No | Must belong to the tenant |
| `sortOrder` | integer | No | 0–10000, default 0 |

**Response** `201 Created` — the created line item.

### `PATCH /invoices/:id/line-items/:lineItemId`

**Auth:** `requireTenant`

### `DELETE /invoices/:id/line-items/:lineItemId`

## Invoice Payments

Both write paths run in one transaction with the invoice row locked
(`SELECT … FOR UPDATE`), so concurrent payments cannot overwrite each other's
totals. `amountPaid`, `balanceDue`, `creditAmount` and `status` are all
re-derived from the payment rows afterwards — none of them is written by hand.

### `POST /invoices/:id/payments`

**Auth:** `requireTenant`

Record a payment. The invoice must be `sent`, `partially_paid` or `overdue` — a
**draft cannot take a payment**, because it has never been sent and recording one
would email a receipt for a document the customer has not seen.

Side effects on success: an `invoice_paid` notification, an E-08 payment receipt
email, and — when the payment closes the invoice and the tenant has a Google
review URL — an E-12 review request scheduled two hours out.

**Request Body:**

```json
{
  "amount": "287.13",
  "paymentDate": "2026-04-05",
  "paymentMethod": "check",
  "referenceNumber": "1234",
  "notes": "Check #1234"
}
```

| Field | Type | Required | Description |
|-------|------|----------|-------------|
| `amount` | **string** | Yes | Positive, up to 2 decimals: `"287.13"`. Not a number. |
| `paymentMethod` | string | No | `cash`, `check`, `credit_card`, `bank_transfer`, `other`. Note the field name — not `method`. |
| `paymentDate` | string | No | `YYYY-MM-DD`. Defaults to today **in the tenant's timezone**. |
| `referenceNumber` | string | No | Max 100 chars |
| `notes` | string | No | Max 2000 chars |

**Response** `201 Created`

```json
{
  "data": {
    "id": "pay_002",
    "invoiceId": "inv_001",
    "amount": "287.13",
    "paymentMethod": "check",
    "paymentDate": "2026-04-05",
    "referenceNumber": "1234",
    "notes": "Check #1234",
    "createdAt": "2026-04-05T10:00:00.000Z"
  },
  "totals": {
    "subtotal": 450,
    "taxAmount": 37.13,
    "totalAmount": 487.13,
    "amountPaid": 487.13,
    "balanceDue": 0,
    "creditAmount": 0,
    "status": "paid"
  }
}
```

An amount above the balance is accepted; the excess lands in `creditAmount`.

**Errors:** `400` — *"Send the invoice before recording a payment against it."* ·
*"This invoice is already paid in full."* · *"Cannot record a payment on a void
invoice"* · archived.

### `POST /invoices/:id/pay-in-full`

**Auth:** `requireTenant`

Record a payment for exactly the outstanding balance, read under the same row
lock that writes it — so there is no stale-balance race. Same guards, side
effects and response shape as `POST /:id/payments`.

**Request Body** (all optional): `paymentMethod`, `paymentDate`,
`referenceNumber`.

**Errors:** `400` — *"This invoice has no outstanding balance"*, plus every error
`POST /:id/payments` can return.

### `DELETE /invoices/:id/payments/:paymentId`

**Auth:** `requireTenant`

Remove a payment and reverse its effect. The resulting status is **derived**, so
deleting the last payment cannot resurrect a void invoice or mark a never-sent
draft as sent.

**Response** `200 OK`

```json
{
  "message": "Payment deleted",
  "totals": { "amountPaid": 0, "balanceDue": 487.13, "creditAmount": 0, "status": "sent" }
}
```

**Errors:** `404` — payment not found · `400` — *"Cannot modify payments on a
void invoice"* · archived.

## Invoice Send / PDF / Void / Status

### `POST /invoices/:id/send`

**Auth:** `requireTenant` · **Rate limit:** 10/min

Render the PDF, store it in the private R2 bucket, move a draft to `sent`, and
email the customer an E-06 with the PDF attached. Re-sending a `partially_paid`
or `overdue` invoice regenerates and re-emails without resetting its status.

**Response** `200 OK` — the updated invoice.

**Errors:** `400` — *"Cannot send a void invoice"* · archived.

### `GET /invoices/:id/pdf`

**Auth:** `requireTenant` · **Rate limit:** 20/min

Stream the stored PDF, or render one on the fly when none is stored. A **void**
invoice always re-renders so the customer receives the watermarked copy rather
than a cached document that still reads as payable.

The tenant logo is only embedded when its URL points into our own R2 public
bucket under that tenant's prefix — `@react-pdf/renderer` fetches remote image
sources from the API process, which made an arbitrary `logoUrl` an SSRF vector.

**Response** `200 OK` — `application/pdf`, `Content-Disposition: inline`.

### `POST /invoices/:id/remind`

**Auth:** `requireTenant` · **Rate limit:** 10/min

Send the E-07 overdue reminder now, rather than waiting for the cron. Claims the
invoice with the same `UPDATE … RETURNING` the cron uses, so pressing twice sends
once.

**Response** `200 OK`

```json
{ "message": "Reminder sent" }
```

**Errors:** `400` — *"Only an unpaid, sent invoice can be reminded about"* ·
*"Set a due date before sending a payment reminder"* · *"A reminder was already
sent for this invoice in the last few minutes"* · archived.

### `POST /invoices/:id/void`

**Auth:** `requireTenant`

Void an invoice. Legal from any status except `paid` and `void`. Deletes the
stored PDF so the next download re-renders with the VOID watermark.

**Response** `200 OK` — the updated invoice.

**Errors:** `400` — *"A paid invoice cannot change status. Delete the payment to
reverse it."* · *"A void invoice is final and cannot change status."* · archived.

### `PATCH /invoices/:id/status`

**Auth:** `requireTenant`

Manual status change, through the transition table. The money statuses are not
reachable by hand — recording or deleting a payment is the only way in.

| From | May move to |
|------|-------------|
| `draft` | `sent`, `void` |
| `sent` | `overdue`, `void` |
| `partially_paid` | `overdue`, `void` |
| `overdue` | `sent`, `void` |
| `paid` | — (terminal) |
| `void` | — (terminal) |

**Request Body:**

```json
{ "status": "sent" }
```

**Response** `200 OK` — the updated invoice.

**Errors:** `400` with an explanatory message, e.g. *"\"paid\" is set by
recording a payment, not by changing the status directly"*.

## Invoice Bulk Operations

All four return `{ succeeded, failed, errors }`. `errors` entries carry the
offending invoice's id, or `"N/A"` for a count of rows that were not found.

### `POST /invoices/bulk-archive`

**Auth:** `requireTenant` · **Body:** `{ "ids": ["inv_001", "inv_002"] }` (1–100 uuids)

Sets `archivedAt`. Already-archived invoices are skipped.

### `POST /invoices/bulk-restore`

**Auth:** `requireTenant` · **Body:** `{ "ids": [...] }`

Clears `archivedAt`. Invoices that are not archived are skipped.

### `POST /invoices/bulk-delete`

**Auth:** `requireTenant` · **Body:** `{ "ids": [...] }`

Hard delete, **draft only**. Non-drafts come back in `errors` with their status.
Stored PDFs are removed from R2 alongside the rows.

### `POST /invoices/bulk-status-update`

**Auth:** `requireTenant`

**Body:** `{ "ids": [...], "status": "void" }`

Runs each invoice through the same transition table as `PATCH /:id/status`, so a
move the detail sheet refuses cannot be smuggled through by selecting the row.
Refused invoices appear in `errors` with the reason. Archived invoices are
skipped.

**Response** `200 OK`

```json
{
  "succeeded": 3,
  "failed": 1,
  "errors": [
    { "id": "inv_009", "message": "INV-2026-0009: A paid invoice cannot change status. Delete the payment to reverse it." }
  ]
}
```

## Invoice From Job

### `POST /invoices/from-job/:jobId`

**Auth:** `requireTenant`

Create an invoice from a job — copies the customer, the line items and the tax
rate, and derives `dueDate` from the tenant's `invoicePaymentTerms`. One
transaction. Refuses when the job already has a non-void invoice.

**Response** `201 Created` — the full invoice row.

**Errors:** `404` — job not found · `400` — *"An active invoice already exists
for this job (INV-…)"* with `existingInvoiceId`.

### `POST /pipeline-stages`

**Auth:** `requireTenant`

Create a custom pipeline stage. `name` is `slugify(label)`.

**Request Body:**

```json
{
  "pipelineId": "pipe_001",
  "label": "Awaiting Parts",
  "color": "purple",
  "lifecycle": "in_progress"
}
```

| Field | Type | Required | Description |
|-------|------|----------|-------------|
| `pipelineId` | string | Yes | Pipeline to add the stage to |
| `label` | string | Yes | Display label, ≤ 60 chars |
| `color` | string | No | Color key (default: `"gray"`) -- see stage color presets |
| `lifecycle` | string | No | `scheduled` (default), `in_progress`, `completed`, `cancelled` |

**About `lifecycle`.** A tenant may call a column anything; the rest of the system needs to
know what a job sitting in it actually *is*. `lifecycle` maps the stage onto one of the four
real job statuses and drives every rule that depends on it — which transitions are legal,
when `completedAt` is stamped, when the E-05 completion email fires, and how the job is
counted in reports. A stage named `awaiting_parts` with `lifecycle: "in_progress"` behaves
exactly like the built-in In Progress column.

It defaults to `scheduled`, which is the safe entry point: a new column can always receive
work. Set it to `completed` and dropping a job there will demand the required checklist
items and email the customer.

**What the UI exposes.** Manage Pipeline only offers `completed` and `cancelled`, as a marker
on a stage rather than a classifier — those are the two that change what happens to a job
rather than just where it sits. Everything unmarked is written as `scheduled`, and any number
of stages may share it. The dialog also keeps the markers exclusive: marking one stage as the
completing stage clears the mark from whichever stage held it, which (per `PATCH` below) also
clears `completed_at` on the jobs in the stage that lost it.

**Response** `201 Created`

```json
{
  "data": {
    "id": "stage_003",
    "pipelineId": "pipe_001",
    "name": "awaiting_parts",
    "label": "Awaiting Parts",
    "color": "purple",
    "lifecycle": "in_progress",
    "sortOrder": 2,
    "isDefault": false
  }
}
```

### `PATCH /pipeline-stages/:id`

**Auth:** `requireTenant`

Update a stage's label, color or lifecycle. Renaming regenerates `name` from the label and
rewrites `jobs.status` for every job pointing at this stage (matched on `stage_id`, so a
job whose status had drifted is corrected rather than missed).

**Request Body:**

```json
{
  "label": "Waiting for Parts",
  "color": "amber",
  "lifecycle": "in_progress"
}
```

Changing `lifecycle` changes what dropping a job into this column does — see
`POST /pipeline-stages` above — and **reconciles the jobs already sitting in the stage**
(2026-08-01). Promoting a stage to `completed` stamps `completed_at` on every job in it that
has none; demoting it away from `completed` clears `completed_at` for all of them. Without
that, marking a stage "Completed" left its existing jobs unstamped, so lifecycle-based counts
and the `completed_at`-based reports disagreed about the same jobs.

**Response** `200 OK`

### `DELETE /pipeline-stages/:id`

**Auth:** `requireTenant`

Delete a pipeline stage.

**Validation Rules:**
- Cannot delete if **any** job points at this stage — archived jobs included. `jobs.stage_id`
  is `ON DELETE SET NULL`, so an archived job excluded from the guard would silently lose
  its column.
- At least 1 stage must remain in the pipeline.

**Response** `200 OK`

```json
{
  "message": "Stage deleted"
}
```

**Error** `409 Conflict`

```json
{
  "message": "Cannot delete stage: 3 job(s) are in this stage. Move them first.",
  "jobCount": 3
}
```
