## 1. What exists today

The invoice domain is the most feature-complete money surface in the product, and
it is genuinely broad:

| Area | Shipped |
|---|---|
| **List** | Search, 6 status tabs, Active/Archived tabs, pagination, next-page prefetch, hover row prefetch, bulk archive/restore/delete, 4 KPI stat cards that double as filters, deep link via `?invoiceId=`, dual view (sheet / full page) with a persisted preference |
| **Detail** | 4 tabs (Details · Line Items · Payments · Photos), inline line-item editing gated to drafts, payment recording, send, void, PDF download, job-linked photo gallery |
| **API** | 20 endpoints — full CRUD, line items, payments, send, PDF, void, manual status, 4 bulk operations, `from-job/:jobId` |
| **Money** | Server-side recalculation on every line-item write, tax rate + discount, `amountPaid` / `balanceDue` tracked, generated `total` column on line items |
| **Numbering** | `INV-YYYY-NNNN` per tenant per year, generated by a DB trigger under a per-tenant `pg_advisory_xact_lock` — the race was correctly fixed in `20260412000001_fix_number_generation_race.sql` |
| **PDF** | `@react-pdf/renderer` document with logo, licence number, payment terms, payment instructions, T&Cs, footer — all tenant-configurable from `/settings/invoices` with a live preview |
| **Email** | E-06 send-with-attachment, E-07 overdue dunning (cron), E-08 payment receipt, E-12 review request |
| **Derived filters** | `overdue` and `unpaid` are computed from `due_date` in the tenant's timezone on both the list and the stats endpoint — the definition unified during the [[dashboard]] audit |

Three things are notably well done and worth keeping as-is:

1. **The advisory-lock numbering trigger.** Correct, idempotent, and per-tenant scoped.
2. **The derived `overdue` / `unpaid` filters** on `GET /invoices` and `GET /invoices/stats`
   (`routes/invoices/index.ts:141-158`, `:251-254`). The comments explain *why* the
   stored status is not trusted. This is exactly the pattern the dashboard audit
   established, applied correctly.
3. **`/settings/invoices`** is the best-built settings page in the app — live PDF
   preview, real error state, sensible tips copy.

**Update (2026-07-29): all 17 rows are now ✅.** The sweeps below were run
repo-wide, not for invoices alone, and the counts are recorded in §7 — which is
itself the process change this section asked for.

**Diagnosis.** Fixes are being applied *to the page being audited* rather than *to
the class, repo-wide*. The one exception proves it: the [[bookings-calendar]] audit
explicitly swept tenant-filter violations across the whole repo and reported "0
remain" — and that sweep largely held. Every pattern that was fixed only in-place
has failed to propagate.

**Recommendation — change the remediation process, not just this page.** Each audit
should end with a repo-wide grep for the class it just fixed, and the sweep result
should be recorded in the report. Concretely, for this backlog:

- Extract `loadEditableInvoice` / reuse `findForeignRef` rather than adding guards handler-by-handler.
- One `LoadErrorState` sweep across all remaining list pages at once, not per audit.
- One `escapeLike` sweep across all seven routes that accept `search`.
- One `tenant-time` sweep across all `components/dashboard/*` that render a date.

That is roughly the same amount of work as fixing invoices alone, and it retires the
finding for `/quotes`, `/assets`, `/catalog` and the rest before they are audited.

## 3. Findings

**Severity:** `P1` breaks correctness or availability · `P2` wrong or inconsistent
numbers · `P3` waste, drift, or noticeable UX defect · `P4` polish.
**Status:** every finding below is now `FIXED` — the text is kept in the present
tense as it was written, because the description of the defect is the useful part.
§7 records what each fix was. Five findings restated still-open entries from
[[deferred-fixes/invoices]], logged 2026-04-12 and never resolved — per
[[strict-rules]] §12 they were due when the payment feature went live, and it is
live. All five are now closed there too.

### 3.1 Critical (P1)

#### INV-01 · No state machine anywhere on `status`; payments accepted on draft and archived invoices `P1`

`POST /invoices/:id/payments` guards only `status === "void"`
(`routes/invoices/index.ts:829`). A **draft** invoice — one the customer has never
seen — accepts a payment, flips to `paid`, fires the `invoice_paid` notification
(`:883`) and emails an E-08 receipt (`:910`) for a document that was never sent.
Archived invoices are equally writable: no mutating handler in this file checks
`archivedAt`.

Worse, `PATCH /invoices/:id/status` (`:1315`) and `POST /invoices/bulk-status-update`
(`:1499`) write **any** of the six enum values with no transition rules at all:
`void → draft` un-voids a cancelled invoice; `draft → paid` records money as received
with zero payment rows while `amountPaid` and `balanceDue` are left untouched.

Jobs got a status transition table in April and a lifecycle-validated
`job-stages.service.ts` in July. Invoices — the money table — has neither.

**Fix:** a single `invoice-status.service.ts` owning every transition, mirroring
`services/job-stages.service.ts`. Reject payments unless status ∈ {`sent`,
`partially_paid`, `overdue`} and `archivedAt IS NULL`.

---

#### INV-02 · `recalculateInvoiceTotals` never revisits status, so an edited invoice stays "Paid" while money is owed `P1`

`routes/invoices/index.ts:46-93` recomputes `subtotal`, `taxAmount`, `totalAmount`
and `balanceDue` — but never `status`. Chain it with INV-01: a draft invoice takes a
payment and becomes `paid`; adding a line item then raises `totalAmount` and
`balanceDue` while `status` stays `paid`. The invoice now reads **Paid** on the list,
in the stat cards, on the PDF and to every consumer of `status`, with an outstanding
balance.

The same function clamps `balanceDue` with `Math.max(0, …)` at three sites
(`:89`, `:877`, `:1045`), so an overpayment is silently destroyed — no credit, no
refund record, no audit trail. That is **DF-INV-01**, open since 2026-04-12.

**Fix:** derive status inside the same transaction that writes the totals; store
overpayment as a credit rather than clamping.

---

#### INV-03 · Deleting a payment resurrects void invoices and marks never-sent drafts as sent `P1`

`DELETE /invoices/:id/payments/:paymentId` (`:977`) has **no status guard**. It sets
`newStatus = "sent"` whenever `amountPaid <= 0` (`:1034`).

- Delete the last payment from a **voided** invoice → it becomes `sent`, and
  re-enters the overdue cron, the aging widget and the outstanding total.
- Delete it from a **draft** → the draft is marked `sent` although nothing was ever
  sent and no PDF exists.

The UI hides the delete button for void invoices
(`invoice-payments-tab.tsx:182`) — so the only guard on this financial reversal lives
in the browser. **DF-INV-03**, open.

---

#### INV-04 · Payment recording is three unsynchronised statements `P1`

`INSERT` payment (`:835`) → `SELECT SUM` (`:849`) → `UPDATE` invoice (`:873`), with
no transaction. Two payments posted concurrently both read a sum and the later
`UPDATE` wins with whatever it saw; a failure between the insert and the update
leaves a payment row the invoice does not know about. `DELETE …/payments/:paymentId`
has the identical shape (`:1001-1049`).

`POST /jobs` was collapsed into one transaction during the jobs remediation
specifically because "a mid-way failure left a job with no checklist". The same
reasoning applies with more force to money. **DF-INV-02**, open.

---

#### INV-05 · The PDF renderer fetches an arbitrary tenant-supplied URL server-side `P1` · **unverified**

`invoice-pdf.tsx:268` renders `<Image src={tenant.logoUrl} />`.
`@react-pdf/renderer` resolves remote image sources by fetching them **from the API
process**. `logoUrl` is validated as `z.string().url().max(2000)`
(`lib/schemas/tenants.ts:33`) — any syntactically valid URL, including
`http://169.254.169.254/latest/meta-data/` or an internal service address.

`GET /invoices/:id/pdf` is the trigger, it has no rate limit (INV-13) and there is no
fetch timeout, so this is both a blind SSRF probe and a request-hang vector.

**Unverified:** I read the code path but did not fire a request, and did not confirm
that this version of `@react-pdf/renderer` fetches rather than skipping remote
sources. **Reproduce before prioritising.** If confirmed, the fix is to require
`logoUrl` to be an R2 URL under the tenant's own prefix — the same rule
[[security-rules]] §10 already applies to storage paths.

### 3.2 High (P2)

#### INV-06 · Three definitions of "overdue"; the cron's disagrees with the two that were unified `P2`

The list (`:149`) and the stats endpoint (`:253`) both derive overdue as
`status NOT IN ('paid','void') AND due_date < (now() AT TIME ZONE <tenant tz>)::date`.
`processOverdueInvoiceReminders` (`lib/cron/email-cron.ts:41-59`) instead uses
`now().toISOString().split("T")[0]` — **server UTC** — and restricts to
`status IN ('sent','overdue')`.

Two consequences:

1. A **`partially_paid`** invoice past its due date is counted as overdue everywhere
   in the UI but **never receives an E-07 reminder**. A customer who paid half and
   then stopped is never chased.
2. For a tenant west of UTC the reminder fires up to a day before the app agrees the
   invoice is late.

#### INV-07 · The overdue cron emails customers about archived invoices `P2`

Same query, no `archivedAt IS NULL` filter (`email-cron.ts:46-59`). Archiving is the
product's "make this go away" action; it does not stop the dunning email. Every other
invoice read path filters archived (`:128`, `:259`).

#### INV-08 · Payment terms are collected, printed on the PDF, and never used to set a due date `P2`

`/settings/invoices` collects `invoicePaymentTerms` ("Net 30") and the PDF prints
`Terms: Net 30` (`invoice-pdf.tsx:335`). But `POST /invoices` sets
`dueDate: body.dueDate ?? null` (`:443`) and `POST /invoices/from-job/:jobId` never
sets `dueDate` at all (`:1588-1596`).

So every invoice raised from a job — the primary flow — has **no due date**: never
overdue, never in an aging bucket, never dunned, and the PDF prints payment terms
above a blank due date. The setting is decorative.

#### INV-09 · `POST /invoices` will copy one customer's job onto another customer's invoice `P2`

Lines `:396-430` validate that `body.jobId` belongs to the tenant, but never that
`job.customerId === body.customerId`. Line items — and therefore the money — are then
copied from that job (`:448-476`). A mis-set `jobId` bills customer A for customer
B's work and links the invoice to B's job. `findForeignRef` was written in July for
exactly this class; it is not used here.

#### INV-10 · A failed list query renders as "no invoices"; a failed stats query renders as zeros `P2`

`invoices-page-client.tsx:176-180` — `invoicesQuery.data?.data ?? []` and
`statsQuery.data?.data ?? {draft:0,…}`, with **no `isError` branch anywhere in the
file**. An API outage shows an empty table reading *"No invoices found for this
filter"* under four zeroed KPI cards.

This is the finding the dashboard, reports and customers audits each fixed
independently. `LoadErrorState` exists at
`components/reusable/load-error-state.tsx` and has **0 imports** here.

#### INV-11 · `/invoices/[id]` renders "page could not be found" for any failure `P2`

`app/(dashboard)/invoices/[id]/page.tsx:15` — `if (error || !invoice) notFound()`.
`getInvoice` does not return a status code, so a 500 or a network blip is
indistinguishable from a genuine 404, and the user is told their invoice does not
exist. The jobs equivalent was fixed on 2026-07-29 by returning `status` and
rendering `JobLoadError`; the change was not carried across.

#### INV-12 · The detail sheet ignores `EntityDetailShell`'s error state `P2`

`invoice-detail-sheet.tsx:99-103` discards the error from `getInvoice` and passes
only `loading` / `hasData` (`:220-221`). `EntityDetailShell` gained `loadError` and
`onRetry` in July precisely because *"the shell rendered nothing for `!loading &&
!hasData`, so a 500 opened an empty sheet"* (`entity-detail-shell/types.ts:30-37`).
Invoices still opens blank.

#### INV-13 · No rate limit on either PDF-rendering endpoint `P2`

`POST /:id/send` and `GET /:id/pdf` both run `generateInvoicePdf` and inherit only
the 100 req/min global bucket (`server.ts:110-113`). 100 concurrent react-pdf renders
will stall the event loop for every tenant on the instance. No `config.rateLimit`
appears anywhere in `routes/invoices/index.ts`.

#### INV-14 · 11 of 20 endpoints are undocumented, and the one payment endpoint that is documented is wrong three ways `P2`

Documented in `API_DOCUMENTATION_3.md`: 9. Missing: `GET /invoices/stats`,
`DELETE /:id/payments/:paymentId`, `POST /:id/send`, `GET /:id/pdf`,
`POST /:id/void`, `PATCH /:id/status`, the four bulk routes, and
`POST /from-job/:jobId`.

In the one payment endpoint that *is* documented (`API_DOCUMENTATION_3.md:297`):

| Doc says | Code does |
|---|---|
| body field `method` | `paymentMethod` (`schemas/invoices.ts:91`) |
| `amount` is a `number` | a **string** matching `^\d+(\.\d{1,2})?$` (`:90`) |
| `paymentDate` **required** | optional (`:94`) |

An integrator following the docs gets a 400 on all three counts. The
`pdfStoragePath` example (`:60`) is also wrong: docs show
`tenants/<id>/invoices/<number>.pdf`, code writes `<tenantId>/<id>.pdf` (`:1122`).

## 4. Product & design observations

Separate from defects — things that are *built correctly* but are the wrong shape for
the user. The target user is a solo contractor doing this on a phone between jobs.

1. **"Mark as paid" is four interactions deep.** The single most common action a
   contractor takes on an invoice — *the customer handed me a cheque* — requires:
   open the row → Payments tab → Record Payment → fill a five-field form → save.
   There should be a one-tap "Paid in full" on the row and in the sheet header that
   posts a payment for the exact balance.
2. **There is no manual "Send reminder".** Dunning is cron-only and fires at most
   once per 24h. A contractor who wants to nudge a customer *now* has no button.
3. **No credit, refund or write-off concept.** Overpayment is destroyed (INV-02);
   partial write-offs are impossible; `void` is the only exit and it is irreversible
   with no reason captured.
4. **No "duplicate invoice".** Recurring work — the maintenance-contract customer
   billed the same amount monthly — has no path other than re-entering every line.
5. **Aging lives on the dashboard, not on `/invoices`.** The page where you chase
   money has four counts; the aging buckets that tell you *which* money to chase are
   on a different page.
6. **Partial payments are invisible on the list.** The Balance column shows a number
   but nothing conveys "$400 of $1,200 paid" — a progress indicator on the row would
   carry the whole story.
7. **The deep link ignores the view preference.** `?invoiceId=` always opens the
   sheet, even for a user who has chosen full-page view.
8. **The empty state is good** — specific, action-led copy. Worth copying to the
   pages that still have generic ones.

## 5. Suggested remediation order

Phase order is chosen so each phase is independently verifiable and no phase
depends on a later one.

### 7.2 The three that were more than they looked

**INV-01/02/03 are one defect.** Not "no state machine" plus "recalculate misses
status" plus "delete resurrects void" — they are all *status being assigned
rather than derived*. Once `deriveStatus()` computes it from the payment rows,
"delete the last payment → set sent" is not expressible: a void invoice stays
void, a never-sent draft stays a draft, and an edited invoice cannot read Paid
while money is owed. The transition table then only has to govern the statuses a
human legitimately chooses (draft → sent → void), which is why `paid` and
`partially_paid` are absent from every row of it.

**INV-06 was worse than "three definitions".** The cron restricted itself to
`status IN ('sent','overdue')`, so a **`partially_paid`** invoice past its due
date was counted as overdue everywhere in the UI and **never received a reminder**.
A customer who paid half and stopped was never chased — a silent revenue leak
that no error, log line or dashboard number would ever surface.

**INV-08 made the primary flow inert.** `POST /invoices/from-job/:jobId` — the
main way invoices get created — set no `dueDate` at all. So those invoices were
never overdue, never in an aging bucket, never dunned, and printed "Terms: Net 30"
above a blank due date. Fixing INV-06 without INV-08 would have fixed the dunning
query for a set that was mostly empty.

### 7.4 Migration applied and verified — 79/79

`20260729000002_invoices_audit_money_model.sql` was applied to Neon on 2026-07-29.

**Structure — 23/23.** The before-state confirmed INV-33 was if anything understated:
`invoice_line_items` and `invoice_payments` had **no index at all** beyond their
primary keys, and `invoices` had only the two the table was created with. All six
new indexes exist with the intended partial predicates, and `EXPLAIN` on an
`invoice_payments` lookup by `invoice_id` now shows an index scan rather than a
sequential one.

**Idempotency — 4 consecutive runs.** Every re-run emits `NOTICE … already exists,
skipping` and nothing higher; the index set and the column set are byte-identical
after each. Verified by capturing `pg_indexes` and `information_schema.columns`
either side of a re-run rather than by reading the `IF NOT EXISTS` clauses.

**The repair `UPDATE`s — 18/18, and this is the part that needed care.** Both
matched **0 rows** when the migration ran, because the invoices table is empty. So
they were applied structurally but proved nothing. They were then exercised against
8 deliberately-corrupt rows inside a transaction that was rolled back — one row per
pattern the audit describes:

| Seeded state | Result | Finding |
|---|---|---|
| `paid`, zero payment rows | → `sent` | INV-01, `PATCH /status` writing money it never received |
| `paid`, total later raised, balance clamped to `0.00` | → `partially_paid`, balance `500.00` | INV-02 |
| `void` with a zero balance | stays `void` | INV-03 — the negative case that matters most |
| genuine `draft` | stays `draft` | must not be promoted to `sent` |
| already-correct `partially_paid` | untouched | the statement's `WHERE` must not churn good rows |
| `amount_paid` $50 over `total_amount` | `credit_amount` = `50.00`, balance `0.00` | INV-02 / DF-INV-01 |

Re-running both statements matched 0 rows, so the repair converges rather than
oscillating. Rollback left the table at 0 rows.

**Service layer round-trip — 38/38** against Neon, exercising the real
`recalculateInvoice` / `deriveStatus` / `splitPayment` / `dueDateFromTerms` /
`canTransition`, not reimplementations. The INV-02 scenario end to end: a $270.63
invoice overpaid by $300 records `paid` with a `29.37` credit; adding a $500 line
item then re-derives **`partially_paid`** with a `511.88` balance and clears the
credit. Before this work that invoice read **Paid**. Also confirmed `Net 30` across
a month boundary (Jan 31 → Mar 02), `void → draft` refused, `draft → paid` refused,
and `overdueCondition()` compiling and running against the tenant's `America/Chicago`.

### 7.5 What is not done
